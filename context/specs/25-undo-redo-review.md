## Findings

1. **High — Retiring the session socket does not stop remaining replay writes.** In `src/collaborate/store/useWorkspaceStore.js:221`, invalidateHistory clears frames/replay and advances the history generation but leaves the sync commit, pending chunks and callback epoch intact. The session subscription at line 854 invokes only that history cleanup. The pump's ownsConnection at line 258 checks the account but ignores session socket ownership, so a late ack still pumps the retired replay on the old socket (`src/collaborate/lib/workspaceSync.js:528`). The history generation protects stack transfer, not actual writes.

   Independently reproduced twice using production stores, the existing authority fake (real applyOps), and a deferred ack: open the 600-edge hub; delete it and settle commit 1; hold commit 2; start undo (the first of its 13 chunks is in flight); set the session socket to null, or replace it with a new socket while retaining the account; verify history/replay clears; release commit 2. Both cases send **14 total commits and restore all 600 edges** instead of stopping at already emitted commit 2. All 12 remaining chunks leave the old connection after session ownership was retired. Both additional assertions fail; existing tests cover only idle history at socket replacement.

   Correct coordination between session ownership, replay/sync invalidation and the pump. On account/session socket retirement, discard unsent replay chunks and retire callbacks immediately. Already emitted work may settle on the server, but its late callback must not send another chunk, re-enable ordinary edits on an unowned binding, or republish a retired optimistic graph. Resume only through authoritative recovery/join on a valid current binding. Do not merely pause old chunks so they resurrect if the old account/socket is restored. Preserve same-account valid retries, new-connection ownership and S24 chat behavior. Add null-socket and replaced-socket tests **during a held multi-commit replay**, plus account change/restore and stale callback coverage proving retired pending work never resumes. Do not weaken production ownership checks to accommodate incomplete fixtures.

2. **Medium — A real React Flow drag cancellation leaves undo/redo disabled.** New gesture tracking clears drag only through onNodeDragStop (`src/collaborate/components/canvas/WorkspaceCanvas.jsx:47`). Cancellation is not wired: the wrapper's onPointerCancel at line 106 only invokes the cursor handler. beginGesture/endGesture otherwise leave the flag set until a workspace invalidation. The spec explicitly requires canceled interactions to clear gesture state.

   This is a supported library path: installed @xyflow/system XYDrag aborts when touchmove has multiple touches (or a dragged node disappears), and its end handler deliberately returns without onNodeDragStop for an aborted drag. Independently exercised the **actual installed XYDrag** with controlled DOM targets/touch events and production store actions: create a saved node; route onNodeDragStart to beginGesture and onNodeDragStop to endGesture, as production does; send one-touch touchstart, two-touch touchmove, then touchend. Start runs once; stop runs zero times. After touches end, `history.gesture` remains true and selectCanUndo false. The added cancellation assertion fails. This is controlled event/module coverage, not a browser run.

   Add binding/interaction-owned cancellation cleanup for drag, resize and connect, including multitouch/removed-node abort paths and pointer cancellation/lost interaction ownership. Cleanup must not dispatch a canceled gesture, clear a newer gesture, or enable replay while an interaction is still active. Preserve normal end-event commit order and cursor behavior. Add production adapter/store regressions for cancellation without an end callback, the actual XYDrag multitouch sequence (or equally direct regression), and normal active/end/disposal paths. Do not change node_modules, disable touch, or wait for turn loss/reload.
